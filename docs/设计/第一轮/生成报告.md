## 一、设计目的

**导入只是为了有数据。这一步才产生价值。**

用户打开应用，3 秒内要看到：这个月花了多少、钱花在哪、跟上月比是多了还是少了。

报告层的三条铁律：

1. **同样的输入永远给同样的输出** —— 不猜、不判断、不解释
2. **只读** —— `reports/` 里不允许出现任何写操作
3. **每个数字可追回原始记录** —— 靠 `v_tx` 视图 + `tx_id`

## 三、真实数据预演

用已导入的 1075 笔微信数据，报告层会输出什么。

### 3.1 周期总览（以 2026-08 为例）

```sql
SELECT ROUND(SUM(amount),2) total, COUNT(*) cnt FROM v_tx
WHERE direction='支出' AND month='2026-08'
```

```
total = ¥2791.43    cnt = 72
prev(2026-07) = ¥918.12
delta = +¥1873.31   rate = +204.1%
```

**注意这里有个现象**：8 月支出是 7 月的 3 倍。原因不是消费增加，而是**7 月有暑假**。

> 这就是为什么报告层必须是纯机械的——它不会告诉你「暑假所以正常」，它只会告诉你数字涨了 204%。**解释权不在这里。**

### 3.2 分类（真实数据暴露的问题）

```
商户消费      707 笔  ¥19625.99
转账           15 笔  ¥8006.90
扫二维码付款     16 笔  ¥1975.01
群收款          47 笔  ¥1111.69
微信红包（单发）  50 笔  ¥952.60
```

**这就是 `tx_type` 太粗的现实。** 一笔美团外卖和一筆便利店购物在平台眼里都是「商户消费」，707 笔挤成一坨。

第一轮的处理：**诚实用 `tx_type`，不加任何猜测的映射。**

```sql
COALESCE(o.manual_category, r.tx_type, '其他') AS category
```

宁可粗，也不要给用户一个「看起来精细、实际靠猜」的分类。`category_rules` 表是第二轮的事。

### 3.3 支付方式

```
平安银行储蓄卡(3106)   286 笔  ¥15486.25
零钱通                387 笔  ¥14061.00
零钱                  162 笔  ¥2124.94
```

**不归并。** `平安银行储蓄卡(3106)` 和 `平安银行储蓄卡(8899)` 是两组——卡号后缀是有意义的信息，合并掉反而丢失信息。

> 168 笔 `pay_method='/'` 的中性交易不在这里，因为它们不是支出。**这正是设计想要的：中性独立成第三类，不被算进收支任何一边。**

### 3.4 趋势

十二个月数据齐全，柱状图直接出。均值线 = 12 个月各自合计的算术平均。

**注意**：`avg` 是 `bars 里 amount 的平均`，**不是** `total / 12`。当期未过完也照常返回（9 月 25 号导出，看到的是截至 25 号的部分）。

## 四、查询层设计

### 4.1 只认视图，不认表

```sql
-- ✅ 所有报告统一这样写
SELECT ... FROM v_tx WHERE direction='支出' AND month='2026-09'

-- ❌ 永远不要
SELECT ... FROM transactions_raw LEFT JOIN tx_overrides ...
```

**好处**：以后修正层加字段、加规则，改 `v_tx` 一行，7 个报告模块**一行都不用动**。

### 4.2 第一轮口径硬编码

```sql
-- views 已内置
CREATE VIEW v_tx_counted AS SELECT * FROM v_tx WHERE is_exempt = 0;
```

⚠️ 第一轮**不做**动态口径（`stats_config` 表 + `config.py` 都不建）。口径硬编码在各自模块里。

等智能层上来、口径真的会频繁变了，再引入 `config.py` 统一翻译 `WHERE` 条件。

### 4.3 索引够用

```sql
CREATE INDEX idx_raw_month_dir ON transactions_raw(month, direction);
CREATE INDEX idx_raw_date      ON transactions_raw(date);
CREATE INDEX idx_raw_year      ON transactions_raw(year, direction);
```

1075 行时全表扫描都比索引快。**索引是为「十万行以后」准备的，不是为现在。**

等真慢了再看慢查询加索引，不要预防性地建一堆。

## 五、数值约定（最容易出错的地方）

| 项 | 约定 | 反例 |
|---|---|---|
| 金额单位 | **元**，`float`，两位小数 | ❌ 分 |
| 谁四舍五入 | **服务端** `round(x,2)` | ❌ 前端 `toFixed` |
| 百分比 | **百分数** `17.2` = 17.2% | ❌ `0.172` |
| `rate` 分母为 0 | 返回 `null`，前端显示「—」 | ❌ 返回 `0` |
| 日历无消费日 | **该日整个不返回** | ❌ `amount: 0` |
| 空列表 | `[]` | ❌ `null` |

> 完整清单见 `../../归档/v0/06_API契约.md`。

## 八、验收标准

- [ ] 每个报告的数字，手工 SQL 查 `v_tx` 能对上
- [ ] 同一请求连跑三次，数字完全一致（确定性）
- [ ] 改一笔 `tx_overrides` 后，报告数字变、原始层未变
- [ ] `reports/` 目录 grep 不到任何 INSERT/UPDATE/DELETE
- [ ] 中性交易不出现在任何收支统计里
- [ ] 日历缺日期的位置前端能补零渲染
- [ ] 金额两位小数，`rate` 为 null 时显示「—」
- [ ] 前端刷新后数字仍然正确（不是本地状态）

## 九、已知的边界情况

| 情况 | 处理 |
|---|---|
| 某月无数据 | `total=0, count=0`，**不是 404** |
| 某分类无小类 | `minors: []` |
| `counterparty` 为空 | 返回 `''`，前端不显示空白 |
| 小类下交易超 200 笔 | `tx_ids` 截断，前端改用 `transactions` 接口 |
| `pay_method` 带卡号 | 不归并，原样返回 |
