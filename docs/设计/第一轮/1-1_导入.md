# 1-1 · 功能一：跨平台账单导入

> 状态：🟡 微信实测通过 / ⚠️ 支付宝待验证 / ⬜ 第三方平台未实现

---

## 一、已有的是什么

微信和支付宝各自能导出一份完整账单。文件格式不同、列名不同、词表不同。

---

## 二、存在什么问题没解决

### 问题 1：格式各不相同

| 平台 | 格式 | 麻烦 |
|---|---|---|
| 微信 | `.xlsx` | **表头在第 18 行**，前面 17 行是账号信息/汇总/备注 |
| 支付宝 | `.zip` → `.csv` | **文件带密码**；编码可能是 GBK/GB18030/UTF-8 |
| 第三方 | `.csv` | 列名每个平台都不一样 |

### 问题 2：词表不统一

微信用 `'/'` 表示中性交易，支付宝写「不计收支」。`备注 = '/'` 表示空，`支付方式 = '/'` 也可能表示空——**但只有中性交易才会这样**。

这些**不实测发现不了**。文档上写的是「空」，实际文件里是斜杠。

### 问题 3：重复导入怎么办

改完分类想再导一次？没有唯一约束的话库里会多一份一模一样的数据，而且没人发现。

### 问题 4：解析到一半失败

1200 笔第 847 笔格式异常。没事务的话库里留下 1~846 笔残缺数据，**界面看着正常，实际永久缺失**。

## 三、提出的设计

### 设计 1：适配器 + 配置驱动

最初设计是 `wechat.py` + `alipay.py` 两个硬编码解析器。实测微信后立刻发现问题：

> 每加一个平台就要复制一遍「打开文件、找表头、认列名、归一化」。美团一个、银行五个，加到第十个时代码就没法维护了。

但实际上，**所有平台的导出账单都是同一个形状**：一张表，行是交易，列是字段。差别只在列名叫什么、文件什么格式。

```
backend/importer/
├── base.py          归一化工具 + Row + dedupe_key
├── wechat.py        需要代码：xlsx + 表头搜索
├── alipay.py        需要代码：加密 zip + 编码探测 + 表头搜索
├── generic_csv.py   通用：绝大多数第三方平台走这里
└── mappings/*.yaml 新平台的列名映射，12 行配置
```

**什么时候写代码，什么时候写 YAML：**

| 情况 | 处理 |
|---|---|
| 列名不一样 | **YAML** |
| 方向/状态词表映射 | **YAML** |
| 文件读不出来（加密 zip） | 代码 |
| 表头不在第一行 | 代码 |
| 数据分散在多处（银行多账户） | 代码 |

**加一个美团 = 放一个 `meituan.yaml`，数据库零结构改动。**

### 设计 2：表头动态搜索，不硬编码行号

```python
def find_header_row(ws, max_scan=40):
    for i, row in enumerate(ws.iter_rows(max_row=max_scan, values_only=True)):
        if row and clean(row[0]) == "交易时间":
            return i
    raise ValueError("未找到表头行")
```

微信那批文件表头在第 18 行，但**导出时间不同、元信息行数会变**。硬编码 `row[17]` 迟早在某次导出时崩。

### 设计 3：dedupe_key 优先用交易单号

```python
if self.tx_no:
    return f"{source}|{tx_no}"              # 99% 的情况
return f"{source}|md5:{...}"                 # 兜底指纹
```

兜底方案**有代价**：同一时刻同一金额同一对手方的两笔真实交易会被误判成重复。

**所以 `skipped`（重复笔数）必须返回给用户看，不能静默吞掉。** 这是整套设计里唯一一处「宁可暴露问题也不假装没事」。

### 设计 4：全事务写入

```python
with db.transaction(conn) as c:
    ensure_platform(c, pid)
    for i, row in enumerate(rows, 1):
        c.execute(INSERT_SQL, ...)
```

任何一行失败 → 整体回滚 → 返回「第 N 行失败，已整体回滚，未写入任何数据」。

### 设计 5：平台自动注册

```python
def ensure_platform(conn, platform_id):
    """导入时自动注册平台。
    不单独做 seed.sql —— 加一个新平台不应该需要改两处地方。"""
```

**这不是设计洁癖，是撞出来的。** 第一次跑就崩了：

```
ValueError: 第 1 行写入失败：FOREIGN KEY constraint failed。已整体回滚
```

`platforms` 表是空的。修法不是加个 seed.sql 手写平台，而是让导入器自己注册。

> 外键约束在建表时不报错，**只在第一次导入真实数据时才炸**。所以「能建表」不等于「能用」。

## 四、归一化规则（实测得出）

| 现象 | 数量 | 处理 |
|---|---|---|
| 微信中性交易 `收/支 = '/'` | 48 笔 | → `direction='中性'` |
| `备注 = '/'` | 大量 | → `''` |
| `支付方式 = '/'` | 168 笔 | → `''`（且全是中性交易） |
| `商户单号 = None` | 部分 | → `''` |

**`'/'` 这个坑不实测发现不了。** 文档上写的是「空」，实际文件里是斜杠。

## 五、实测结果

```
✅ 微信解析 1058 笔
   支出/收入/中性 与账单文件自带的汇总数字分毫不差
✅ 重复导入：0 写入 / 1058 跳过
✅ 解析失败 → 整体回滚，一条都没写进去
✅ 脏值归一化正确
```

**「与账单自报汇总分毫不差」是这里最硬的一条**——它证明解析器没有丢行、没有吞行、没有把中性算进收支。

## 七、已知风险

| 风险 | 后果 | 缓解 |
|---|---|---|
| 兜底 dedupe_key 误判 | 真实交易被当重复丢弃 | `skipped` 暴露给用户 |
| 支付宝 ZIP 密码遗失 | 无法导入 | 用户重新导出 |
| 表头行号变化 | 解析失败 | 已改为搜索 |
| 金额单位不一致（有的平台导分） | 数字差 100 倍 | 各 adapter 负责归一化，测试要覆盖 |
