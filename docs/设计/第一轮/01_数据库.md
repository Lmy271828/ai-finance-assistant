# 01 · 数据库

> 两个文件：`db/schema.sql`（建表语句）和 `backend/db.py`（连接管理）。
> 一句话：**前者定义长什么样，后者负责让它真的存在、且安全地存在。**

---

# 一、`db/schema.sql`

## 已有的是什么

微信一份 CSV，支付宝一份 CSV。想存起来，最朴素的做法是两张表各存各的。

## 存在什么问题没解决

**两张表 = 两个世界的口径。** 每个查询都要记得手动 UNION，漏一边数字就错。而且两边列名不一样，光对齐就得写一堆转换代码。

第三个问题更隐蔽：**去重。** 同一份账单导两次怎么办？没有唯一约束的话，库里会多一份一模一样的数据，而且没人发现。

## 提出的设计

### 1. 一张表装所有平台

```sql
CREATE TABLE transactions_raw (
    source       TEXT NOT NULL,   -- '微信支付' / '支付宝' / '美团' / ...
    platform_id  TEXT NOT NULL REFERENCES platforms(id),
    tx_time      TEXT NOT NULL,
    direction    TEXT NOT NULL CHECK (direction IN ('支出','收入','中性')),
    amount       REAL NOT NULL CHECK (amount > 0),
    pay_method   TEXT,
    counterparty TEXT,
    item         TEXT,
    tx_type      TEXT,
    status       TEXT,
    tx_no        TEXT,
    merchant_no  TEXT,
    remark       TEXT,
    -- 派生字段
    date, month, year, weekday, hour,
    -- 导入元信息
    dedupe_key   TEXT NOT NULL UNIQUE,
    raw_json     TEXT NOT NULL,
    imported_at, import_batch
);
```

三个设计点：

| 设计 | 解决什么 |
|---|---|
| `source` 自由文本 + `platform_id` 外键 | 加新平台不用改表结构 |
| `CHECK (direction IN (...))` | 脏数据在**写入那一刻**就被拦下，不等到出报表才发现 |
| `UNIQUE (dedupe_key)` | 重复导入自动跳过 |
| `raw_json NOT NULL` | 归一化是我们做的判断，错了能翻回原始行 |

### 2. 原始层与修正层分开

```sql
CREATE TABLE tx_overrides (
    tx_id           INTEGER PRIMARY KEY REFERENCES transactions_raw(id),
    manual_category TEXT,          -- 手动大类
    manual_subcat   TEXT,          -- 手动小类
    is_exempt       INTEGER DEFAULT 0,   -- 豁免：不计入统计
    funding         TEXT DEFAULT '自有',
    note            TEXT,
    updated_by      TEXT,          -- 'ui' / 'mcp'
    updated_at      TEXT
);
```

**一张凭证表 + 一张修正表。** 改一笔只动第二张。

`updated_by` 看起来多余，但它是这套设计能自证的关键——三个月后你查一眼就知道「这笔是人改的还是 AI 改的」。**可追溯不靠注释，靠字段。**

### 3. 导入批次

```sql
CREATE TABLE import_batches (
    batch_id, platform_id, filename,
    total, inserted, skipped, failed, date_from, date_to
);
```

`skipped`（重复笔数）必须能被查到。兜底 dedupe_key 有误判风险，静默吞掉就是数据丢失。

### 4. 视图把两层缝起来

```sql
CREATE VIEW v_tx AS
SELECT r.*,
    COALESCE(o.manual_category, r.tx_type, '其他') AS category,
    COALESCE(o.is_exempt, 0)                    AS is_exempt,
    COALESCE(o.funding, '自有')                 AS funding
FROM transactions_raw r
LEFT JOIN tx_overrides o ON o.tx_id = r.id;
```

**查询只认 `v_tx`，不关心数据现在在哪一层。**

以后修正层加字段、加规则，改这里一行，7 个报告模块**一行都不用动**。

### 5. 索引

```sql
CREATE INDEX idx_raw_month_dir ON transactions_raw(month, direction);
CREATE INDEX idx_raw_date      ON transactions_raw(date);
CREATE INDEX idx_raw_year      ON transactions_raw(year, direction);
```

只建 3 个。**索引是为「十万行以后」准备的，不是为现在。** 1000 行时全表扫描都比索引快。等真慢了，看慢查询再加，不要预防性地建一堆。

# 二、`backend/db.py`

## 已有的是什么

有了 `schema.sql`，我们在命令行里跑一句 `sqlite3 bills.db < schema.sql` 就能把表建出来。第一轮看起来够了。

## 存在什么问题没解决

### 问题 1：每个人都要手动建表

队友 clone 你的仓库，他本地 `bills.db` 是空的（`.db` 不进 git，每人账本都不一样）。他必须自己记得建。

一周后新人加进来问「为什么前端报错说表不存在」，答案永远是「你忘了建表」。

### 问题 2：改了 schema，队友的库对不上

你加了 `funding` 字段，他没跑那句 SQL。

**表现是运行时报错，而不是启动时报错**——更糟，他跑到第 37 笔交易才崩，前 36 笔白跑。

### 问题 3：路径写错，SQLite 不报错

SQLite 有个坑：**路径不存在时不会报错，会默默创建一个空的。**

用相对路径 `"db/bills.db"` 写代码，同一段代码在不同工作目录下会指向三个不同的库。症状是「数据怎么一条都没有」，而不是报错。排查极费时间。

### 问题 4：导入中断会静默丢数据 ⚠️ 最要命

导入 1200 笔，第 847 笔格式异常。

**没有事务管理的话：**

```
第 1~846 笔：已写入 ✅
第 847 笔：失败 ❌
第 848~1200 笔：未执行 ❌
```

库里现在是残缺的 846 笔。界面显示「9月 846 笔」，数字看着正常，但你不知道少了 354 笔。

**下次再导一遍**，因为 `dedupe_key` 唯一约束，前 846 笔被跳过——你得到一个**看起来完整、实际永久缺失**的账本。

## 提出的设计

```python
DB_PATH = BASE_DIR / "db" / "bills.db"        # 绝对路径
SCHEMA_PATH = BASE_DIR / "db" / "schema.sql"

def init_db(): ...                # 建表建视图，幂等，可重复跑
def get_conn(): ...               # row_factory + WAL + busy_timeout
@contextmanager
def transaction(): ...            # BEGIN / COMMIT / ROLLBACK
```

### 1. `init_db()` —— 把建表收进代码

```python
conn.executescript(SCHEMA_PATH.read_text(encoding="utf-8"))
```

`CREATE TABLE IF NOT EXISTS` + `executescript` 是**幂等**的，所以可以重复执行，也可以在服务启动时自动跑：

```python
@app.on_event("startup")
def startup(): db.init_db()
```

于是队友好、库不一致、新人上手，**全部消失**。「表不存在」这类问题在启动阶段暴露，不会在第 37 笔交易的时候暴露。

### 2. `get_conn()` —— 一次配好

```python
conn.row_factory = sqlite3.Row                              # row['amount'] 而不是 row[3]
conn.execute("PRAGMA journal_mode=WAL;")                     # 读写不互斥
conn.execute("PRAGMA busy_timeout=5000;")                    # 写冲突时等待而非立刻报错
```

**WAL 是必须的**——FastAPI 默认用线程池跑同步函数，而 SQLite 不允许多线程同时写库，不开 WAL 第二个写事务立刻抛 `database is locked`。

**为什么统一写在 `db.py`**：如果每个模块自己 `sqlite3.connect()`，一定有人忘了设 `row_factory`，然后写出一堆 `row[3]` 魔法下标，三个月后没人记得第 3 列是哪个字段。

### 3. `transaction()` —— 全进或全不进

```python
with db.transaction(conn) as c:
    for i, row in enumerate(rows, 1):
        c.execute(INSERT_SQL, row)
# 任何异常 → ROLLBACK
```

导入失败时整体回滚，返回明确错误：

```
「第 847 行金额列无法解析，已回滚，未写入任何数据」
```

**要么全进，要么全不进，中间状态不允许存在。**

> ⚠️ 这不是理论。实际跑的时候真的撞上过一次：第一次导入时 `platforms` 表是空的，外键失败，**一条都没写进去**，错误精确到第 1 行。没有事务的话这里就是半截数据。

### 4. 原始层的不可变性靠什么保证

**不靠「大家记得别 UPDATE」，靠三样东西：**

1. 业务上：原始字段只写一次
2. 代码里：除了 `importer/`，没有任何写 `transactions_raw` 的语句
3. 测试里：`grep -r "UPDATE transactions_raw"` 全项目零命中

第 3 条可以随时现场演示。**这不是口号，是能跑出来的命令。**
