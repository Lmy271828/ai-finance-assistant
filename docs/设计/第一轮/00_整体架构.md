# 00 · 整体架构

> 第一轮整体设计的骨架。后面 01~04 是各层展开，1-1~1-3 是三个功能展开。

---

## 一、已有的是什么

用户手里有微信和支付宝两份账单导出文件。每份都是一张二维表：行是交易，列是字段。

这两张表已经能回答不少问题——用 Excel 透视表拖两下，「这个月花了多少」当场就有答案。

---

## 二、存在什么问题没解决

### 问题 1：两份表拼不到一起

微信那列叫「交易类型」，支付宝叫「交易分类」；微信叫「商品」，支付宝叫「商品说明」；微信的「收/支」为空表示不计收支，支付宝直接写「不计收支」。

要合并成一个总数，就得先问自己：微信的算不算，支付宝的算不算？漏一边，数字就错，而且**错得很安静**。

### 问题 2：改一笔就把凭证涂改了

发现某笔被分错类，最自然的做法是 UPDATE 那一行。

但三个月后你再也分不清哪些分类是你改的、哪些是平台原本标的。更糟的是，导给朋友的账单无法复核——**账单是凭证，凭证涂改等于伪造**。

### 问题 3：口径变了，历史数字跟着变

「以后美团、某快餐都算餐饮」——改的是规则。

如果规则和数据混在同一张表里，改规则的瞬间所有历史统计全变，上个月刚做的分析当场作废。

---

## 三、提出的设计

### 设计 1：导入时把两个平台抹平成一张表

```
微信 .xlsx  ┐
            ├─→ transactions_raw（一张表，source 字段标明来源）
支付宝 .csv ┘
```

归一化在导入时一次做完，后面所有查询只认这一张表。

### 设计 2：原始凭证和修正分成两层

```
transactions_raw    原始凭证，导入时 INSERT，之后永不 UPDATE
tx_overrides        所有修正落这里
        ↓
     v_tx 视图        把两层缝起来，查询只认它
```

改一笔 → 只动 `tx_overrides`。原始数据一个字节没动。

**具体怎么做到，见 02_数据库.md。**

### 设计 3：三条通道，各有唯一的门

这是整个架构最重要的一条。**不是「所有请求先过校验再过权限」，而是三条互不相干的通道。**

```
┌──────────────────────────────────────────────────┐
│  写原始层   唯一入口 backend/importer/           │  只能 INSERT
│             ← 导入账单                             │
├──────────────────────────────────────────────────┤
│  写修正层   唯一入口 backend/overrides.py         │  UPSERT + 403
│             ← 前端改分类 / AI 改分类              │
├──────────────────────────────────────────────────┤
│  读         backend/reports/*.py                  │  纯 SELECT，查 v_tx
│             ← 所有报告查询                         │
└──────────────────────────────────────────────────┘
```

**三件事要说清楚：**

1. **`schemas.py` 不在任何一条通道上**。它是 HTTP / MCP 边界的类型校验，校验完就把数据交给业务函数，**自己不碰数据库**。

2. **查询不经过 `overrides.py`**。它只管「改」，不管「读」。报告直接查 `v_tx`。

3. **越权在结构上不可达**。AI 想改原始数据？`overrides.py` 里根本没有那条代码路径，不是「约定不许」，是「没有」。

## 四、四层结构

```
       浏览器前端                      外部 AI 客户端
           │                              │ MCP
           ↓                              ↓
      ┌────────────────────────────────────────┐
      │         backend/main.py（入口）          │
      └────────────────────────────────────────┘
                     │
     ┌───────────────┼───────────────┐
     ↓               ↓               ↓
  importer/      reports/      overrides.py
   （写原始）      （只读）        （写修正）
     └───────────────┼───────────────┘
                     ↓
                  db.py（连接 / 事务 / 建表）
                     ↓
                  bills.db
```

**前端和 AI 最终调的是同一批 Python 函数。**

理由：如果两边各写一套，会出现「前端显示 A，AI 算出 B」，口径立刻分裂，而且没人知道该信哪个。

---

## 五、这套设计换来的三件事

| | 怎么做到的 |
|---|---|
| **数字可信** | 原始数据不可改，任何数字都能追回原始记录 |
| **口径可迭代** | 改规则重跑查询即可，历史报表不会消失 |
| **能自查** | `updated_by` 记录每笔修正是人改的还是 AI 改的 |
