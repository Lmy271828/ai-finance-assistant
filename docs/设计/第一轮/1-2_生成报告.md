# 1-2 · 功能二：生成 preset 报告

> 状态：✅ 7 个接口全部跑通（真起 uvicorn + 1058 笔真实数据实测）

---

## 一、已有的是什么

导入之后，库里已经有了一整年的真实流水。`SELECT SUM(amount) GROUP BY month` 就能出数。

## 二、存在什么问题没解决

### 问题 1：用户要的不是「能算」，是「看得懂」

"这个月花了多少" 是一句话。但支付宝用一屏回答了它：总额、环比、每日日历、近 5 月柱状图、月均参考线。

**这些组件没有一个是 SQL 自动长出来的，是产品设计。**

### 问题 2：`tx_type` 太粗，直接用没法看

真实数据跑出来是这样：

```
商户消费      707 笔  ¥19625.99
转账           15 笔  ¥8006.90
扫二维码付款     16 笔  ¥1975.01
```

一笔美团外卖和一笔便利店在平台眼里都是「商户消费」，**707 笔挤成一坨**。

### 问题 3：口径分母容易搞错

分类占比的分母是**周期总额**，不是各大类之和。所以各大类占比加起来可能 **< 100**，差额是未分类部分。

不写清楚，前端会以为算错了。

## 三、提出的设计

### 设计 1：7 个组件，一一对应页面上的区块

| # | 组件 | 接口 | 关键约定 |
|---|---|---|---|
| 1 | 周期总览 | `/api/report/summary` | 上期为 0 时 `rate` 返回 `null`（不是 0） |
| 2 | 每日日历 | `/api/report/calendar` | **无消费日整个不返回**，不是 `amount: 0` |
| 3 | 趋势 + 均值线 | `/api/report/trend` | `avg` 是 bars 的平均，**不是 `total / n`** |
| 4 | 分类环形图 | `/api/report/by-category` | `minors` 为空时是 `[]` 不是 `null` |
| 5 | 支出方式 | `/api/report/by-method` | 按原始字符串分组，**不归并卡号** |
| 6 | 收入排行 | `/api/report/income-rank` | `counterparty` 可能为空字符串 |
| 7 | 明细列表 | `/api/report/transactions` | `date_from/to` **覆盖** period |

### 设计 2：第一轮诚实用 `tx_type`，不硬造映射

没有规则映射表的时候，分类直接：

```sql
COALESCE(o.manual_category, r.tx_type, '其他') AS category
```

**宁可粗，也不要给用户一个「看起来精细、实际靠猜」的分类。**

真实数据证明了为什么：707 笔挤成「商户消费」确实难看，但硬造一套关键词映射只会让错误看起来像正确。`category_rules` 表是第二轮智能层的事。

### 设计 3：查询只认视图

```sql
-- ✅ 所有报告统一这样写
SELECT ... FROM v_tx WHERE ...

-- ❌ 永远不要
SELECT ... FROM transactions_raw LEFT JOIN tx_overrides ...
```

以后修正层加字段、加规则，改 `v_tx` 一行，**7 个报告模块一行都不用动**。

### 设计 4：口径硬编码在各自模块

第一轮**不做**动态口径（`stats_config` 表 + `config.py` 都不建）。

现在口径变化不频繁，硬编码在各自 `reports/*.py` 里。等智能层上来、口径真的频繁变了，再引入统一翻译。

### 设计 5：只建 3 个索引

```sql
idx_raw_month_dir (month, direction)
idx_raw_date      (date)
idx_raw_year      (year, direction)
```

1000 行时全表扫描都比索引快。**索引是为十万行以后准备的。** 等真慢了看慢查询再加。

## 四、真实数据预演

以 2026-08 为例（数字来自实际查询）：

```
8月支出  ¥2791.43  (72 笔)
7月支出  ¥918.12   (36 笔)
环比     +204.1%
```

**原因不是消费增加，是 7 月放暑假。**

> 这正是报告层必须纯机械的价值——它只会告诉你「涨了 204%」，
> **不会**告诉你「暑假所以正常」。**解释权不在这一层。**

分类（2026-08）：

```
商户消费      ¥1695.17   60.7%
扫二维码付款    ¥919.00    32.9%
微信红包（单发） ¥81.66     2.9%
             ─────────────────
占比合计       99.9%    ← 差额是未分类部分
```

## 六、文件划分

```
backend/reports/
├── __init__.py
├── _common.py       公共工具（方向映射、周期展开、四舍五入、占比）
├── summary.py       组件 1
├── calendar.py      组件 2
├── trend.py         组件 3
├── category.py      组件 4
├── method.py        组件 5
├── income_rank.py   组件 6
└── transactions.py  组件 7
```

**一个组件一个文件，每个函数一个 SELECT。** 谁拿到哪几条，自己写自己测。

### 硬约束

> **本包只有 SELECT。** 不允许 INSERT / UPDATE / DELETE。
> 理由：账本可信的前提之一是「报告只读，不改数据」。

---

## 七、边界情况

| 情况 | 处理 |
|---|---|
| 某月无数据 | `total=0, count=0`，**不是 404** |
| 某分类无小类 | `minors: []` |
| `counterparty` 为空 | 返回 `''`，前端不显示空白 |
| 小类下交易超 200 笔 | `tx_ids` 截断，前端改用 `transactions` 接口 |
| `pay_method` 带卡号 | **不归并**，原样返回 |
