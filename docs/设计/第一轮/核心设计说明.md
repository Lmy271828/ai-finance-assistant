## 三、四层结构

```
              ┌──────────────────┐
              │   浏览器前端      │
              └────────┬─────────┘
                       │ HTTP / JSON
              ┌────────▼─────────┐
  ┌──────────►│  FastAPI 入口    │◄───────────┐
  │           │  backend/main.py │            │
  │           └────────┬─────────┘            │
  │                    │                     │
┌─┴──────────┐  ┌──────▼──────┐      ┌────────┴─────┐
│  导入器     │  │  报告模块    │      │  overrides   │
│ importer/  │  │  reports/   │      │  修正唯一入口 │
└─┬──────────┘  └──────┬──────┘      └────────┬─────┘
  └────────────────────┴─────────────────────┘
                       │
                 ┌─────▼──────┐
                 │   db.py    │  连接 / 事务 / 建表
                 └─────┬──────┘
                       │
                 ┌─────▼──────┐
                 │  bills.db  │  原始层 + 修正层 + 视图
                 └────────────┘

                 ┌──────────────────┐
                 │  外部 AI 客户端   │ Claude / 豆包 / …
                 └────────┬─────────┘
                          │ MCP
                 ┌────────▼─────────┐
                 │  mcp/server.py   │
                 └────────┬─────────┘
                          └──── 调同一批 Python 函数
```

**两条入口，一条逻辑。** 前端和 AI 调的是同一批函数——否则会出现「前端显示 A，AI 算出 B」，口径立刻分裂。

## 四、数据库分层的意义

```
transactions_raw    原始凭证，导入时 INSERT，之后永不 UPDATE
tx_overrides        修正层，前端与 AI 均可写
import_batches      导入批次，记住每次导了多少、跳过多少
platforms           平台元数据，导入器自动注册
        ↓
     v_tx 视图        把两层缝起来，报告只认它
```

**为什么必须分两层** —— 真实账本里遇到的实际情况：

| 真实案例 | 正确做法 | 错误做法 |
|---|---|---|
| 「某高校天猫校园店」被归成学习，其实是零食 | 写 `tx_overrides.manual_category` | UPDATE 原始 `tx_type` |
| 关键词「华颐」误抓售货机 | 收窄规则 | 删掉原始记录 |
| 口令红包是资金调拨不是消费 | 设 `is_exempt=1` | 删掉这笔 |

**原始凭证一旦被涂改，导出的账单就既不能追溯也不能复核。**

## 八、契约：`schemas.py` 是唯一真相源

```
        schemas.py
             │
     ┌───────┼────────┬──────────┐
     ↓       ↓        ↓          ↓
  FastAPI  OpenAPI  MCP工具    前端types.ts
```
