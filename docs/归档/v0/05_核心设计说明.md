## 二、数据库层：设计目的

### `db/schema.sql` —— 唯一的真相源

**设计目的**：把表结构写死成一个可重复执行的文本文件。

**不做会怎样**：每个人脑子里一套表结构，A 改了三张表，B 还在按老结构写 SQL，联调时才发现库结构不一样。

**配套的 `bills.db` 是运行时生成的，不进 git**——每个人的账本都不一样。

---

### 原始层 `transactions_raw` —— 凭证不可涂改

**设计目的**：**证明账本可信的唯一手段。**

只要原始记录能被改，任何一个数字都不可信。你三个月后导出给朋友的账单，无法验证、无法复核、无法追责。

**所以有两道保险：**
1. 业务上：原始字段**只写一次**
2. 技术上：`grep -r "UPDATE transactions_raw"` 全项目零命中

---

### 修正层 `tx_overrides` —— 所有人工/AI 修正的落点

**设计目的**：让"改一笔"和"改原始数据"**在结构上分离**。

用户说"这笔是零食不是学习"，我们不去改 `tx_type`，而是在 `tx_overrides` 写一行 `manual_category='零食超市'`。

**好处不只是"保留原始"**，更重要的是：

| 场景 | 做法 | 结果 |
|---|---|---|
| 改一笔分类 | 写 `tx_overrides` 一行 | 只影响这一笔 |
| 改一条全局规则 | 改 `category_rules` 一条 | 全部历史报表按新口径重算 |
| 回退 | 删掉那一行/停用那条规则 | 数字回到原样 |

**原始数据从头到尾一个字节没动过。**

---

### 视图 `v_tx` —— 把两层缝在一起

**设计目的**：让所有查询只认一个视图，**不关心数据现在是在原始层还是修正层**。

```sql
COALESCE(o.manual_category, r.tx_type) AS category
COALESCE(o.is_exempt, 0)              AS is_exempt
COALESCE(o.funding, '自有')           AS funding
```

报告模块永远 `FROM v_tx`，永远看不到 JOIN。修正层以后加字段、加规则，视图改一行，7 个报告模块**一行都不用动**。

## 三、后端：每个文件的设计目的

### `backend/db.py` —— 底层地基

**设计目的**：把三件容易做错的事统一收口。

| 职责 | 不做的后果 |
|---|---|
| 执行 `schema.sql` | 新人/CI 拿到空库，报错出现在业务跑到一半时 |
| 绝对路径 + `row_factory` | 相对路径写错地方，SQLite 默默建新空库，症状是"数据不见了"；`row[3]` 魔法下标满天飞 |
| 事务边界 | **导入中断 → 静默丢数据**，界面数字看着正常，实际永久缺失 |

**所有模块拿连接只能经过它**，没有例外。

---

### `backend/schemas.py` —— 唯一契约

**设计目的**：**同时解决三个问题，且它们其实是同一件事。**

| 解决什么 | 怎么解决 |
|---|---|
| AI 不知道有哪些接口 | Pydantic 模型 → 自动生成 MCP 工具 schema |
| 前端不知道返回什么形状 | 同一份模型 → `/docs` 里能看到字段说明 |
| 脏参数打到最后才崩 | `Literal['expense','income']` 在入口就拦下 |

**它还有个隐藏作用**：`OverrideIn` 里**故意不声明任何原始字段名**。AI 从协议层面就传不进 `amount`。

---

### `backend/overrides.py` —— 写权限的唯一门

**设计目的**：把"原始数据不许改"从**约定**变成**结构**。

```
前端 PATCH /api/tx/1/override ─┐
                               ├─→ overrides.set_override()
MCP  tool: set_override ────────┘
              ↑
        唯一校验点（只有这一份代码）
```

如果校验写在两个地方，早晚会漏一处，AI 就能绕过。而这正是我们最核心的卖点。

**判断标准**：`overrides.py` 里**不存在任何**针对 `transactions_raw` 的 UPDATE/DELETE 路径。这不是纪律，是物理事实。

---

### `backend/main.py` —— 入口，业务逻辑零容忍

**设计目的**：处理"谁触发了什么函数"的路由问题。

**它做**：注册路由、启动建表、统一错误响应、CORS。

**它不做**：任何业务判断。看到 `if month == '2026-09':` 就是逻辑漏进来了。

---

### `backend/importer/` —— 见第五节（多平台）

### `backend/reports/` —— 7 个纯查询模块

**设计目的**：一个组件一个文件，每个函数一个 SELECT。

**设计约束**：**这些文件里不能有任何写操作。** 报告是只读的，这是账本可信的前提之一。

## 四、前端：每个文件的设计目的

### `frontend/vite.config.ts` —— proxy

**设计目的**：让前端代码里**永远不出现 `http://localhost:8000`**。

```typescript
server: { proxy: { '/api': { target: 'http://localhost:8000' } } }
```

**不做会怎样**：队友一定会硬编码绝对地址。开发时能跑，部署时全挂。**这是本项目最容易被忽略、返工代价最高的一行配置。**

---

### `frontend/src/api/` —— 薄薄一层，不是重点

**设计目的**：统一 `baseURL` 和错误处理。

```typescript
const BASE = '/api'   // ← 走 vite proxy，永远不写绝对地址
```

**它可以很薄**。不封装业务函数（`getSummary()` 这种），队友直接 `fetch` 也行——只要 `BASE` 是共享的、错误处理是一致的。

> 是否要写完整 11 个包装函数：**可选**。写了舒服，不写也能活。别在这上面花半天。

---

### `frontend/src/api/types.ts` —— 从后端抄

**设计目的**：TS 类型 = 后端 Pydantic 模型的一比一翻译。

```typescript
export interface SummaryResp {
  total: number       // 元，两位小数
  prev:  number
  delta: number
  rate:  number | null // 百分数，17.2 表示 17.2%
  count: number       // 笔数
}
```

**这个文件必须和 `schemas.py` 同步改**。这是"契约"两个字的实际含义。

---

### `frontend/src/router/index.ts` —— URL 是契约

**设计目的**：前端路由参数名必须和后端查询参数名**一模一样**。

```
/bill?type=expense&period=month&value=2026-09
      ↑ 与后端 ?type=&period=&value= 一一对应
```

**不定会怎样**：队友想叫 `kind` 还是 `type`，后端就得跟着改，改了另一边全崩。

---

### `frontend/src/styles/variables.css` —— 定变量不定样式

**设计目的**：防止三个人挑出三个红。

```css
--color-expense: #e5484d;
--color-income:  #30a46c;
--space-1..4;  --radius;
```

**你定色板和间距刻度，队友定布局。**

---

### `frontend/src/views/*.vue` —— 带骨架标记的壳

**设计目的**：**不是代码，是省沟通。**

每个组件区块用 `data-component` 标出来：

```vue
<section data-component="summary">小结放这儿</section>
<section data-component="calendar">日历放这儿</section>
<section data-component="trend">柱状图放这儿</section>
<section data-component="category">分类放这儿</section>
```

队友打开文件就知道东西放哪，**不用问**。

---

### `frontend/src/components/` —— 具体业务的具体组件

9 个纯 UI 零件，接口约定清楚，没有歧义：

```
TimeSelector  TypeToggle  DayCalendar  TrendBar
CategoryPie   CategoryList  MethodList  IncomeRank
DayDetail
```

## 五、导入：多平台架构

### 已有的是

第一版设计只支持微信和支付宝两个解析器：`wechat.py` + `alipay.py`。

### 存在的问题是

目标要求"支持尽可能多的平台：美团、各类银行卡……"。用两个硬编码解析器去扩展，会变成这样：

```
wechat.py    180 行
alipay.py    220 行   （要处理 ZIP + GBK 编码探测）
meituan.py   ???
cmb.py       ???
boc.py       ???
icbc.py      ???
```

**每加一个平台就是复制粘贴一遍前三步——打开文件、找表头、认列名、归一化。**

而实际上，**所有平台的导出账单都是同一个形状**：一张表，行是交易，列是字段。差别只在**列名叫什么**、**文件是什么格式**。

### 所以引入：适配器 + 配置驱动

```
backend/importer/
├── __init__.py        # 平台注册表
├── base.py            # PlatformAdapter 协议 + 归一化函数
├── registry.py        # 按文件特征识别平台
├── adapters/
│   ├── wechat.py      # 需要代码：xlsx + 表头偏移
│   ├── alipay.py      # 需要代码：ZIP + 编码探测
│   ├── generic_csv.py # 通用：绝大多数第三方平台走这里
│   └── bank.py        # 需要代码：多账户合并
└── mappings/
    ├── meituan.yaml   # 只是配置，不用写代码
    ├── cmb.yaml
    └── icbc.yaml
```

#### `base.py` 定义的协议

```python
class PlatformAdapter(Protocol):
    name: str                    # '微信支付' / '美团' / '招商银行'
    def detect(cls, filename, head) -> float: ...   # 识别置信度 0~1
    def parse(cls, raw) -> Iterator[Row]: ...        # 产出归一化行
```

#### 第三方平台的配置长这样（`mappings/meituan.yaml`）

```yaml
name: 美团
filenames: ["美团*.csv", "*美团*"]
columns:
  交易时间:  tx_time
  订单号:    tx_no
  商家名称:  counterparty
  订单金额:  amount
  收/支:     direction
  支付方式:  pay_method
  交易状态:  status
direction_map:
  支出: 支出
  收入: 收入
status_filter:
  - 已取消
  - 已关闭
```

**加一个美团，写 12 行 YAML，不写一行 Python。**

#### 什么时候才需要写代码

只有这三种情况：

| 情况 | 例子 | 为什么代码解决不了 |
|---|---|---|
| 格式本身特殊 | 支付宝 ZIP + GBK 编码探测 | 文件读不出来，配置无从下手 |
| 表头不在第一行 | 微信 xlsx 前面有说明文字 | 得先找到真正的表头行 |
| 数据分散在多处 | 银行账单一个 PDF 里多个账户 | 得合并多个数据源 |

**除这三种，其余全部配置化。**

---

### 由此带来的 schema 变化

`source` 不能再是固定两个值，要放开：

```sql
-- ❌ 原来这样写，第二轮就炸了
source TEXT NOT NULL CHECK (source IN ('微信支付','支付宝'))

-- ✅ 改成这样
source TEXT NOT NULL          -- 自由文本，'微信支付'/'美团'/'招商银行'/...
platform_id TEXT               -- 外键指向 platforms 表
```

配套一张平台元数据表：

```sql
CREATE TABLE platforms (
    id          TEXT PRIMARY KEY,     -- 'wechat' / 'alipay' / 'meituan'
    name        TEXT NOT NULL UNIQUE, -- 显示名 '微信支付'
    kind        TEXT NOT NULL,        -- 'wallet' 钱包 / 'bank' 银行 / 'ecommerce'
    adapter     TEXT NOT NULL,        -- 'generic_csv' / 'wechat' / ...
    enabled     INTEGER NOT NULL DEFAULT 1,
    created_at  TEXT NOT NULL DEFAULT (datetime('now'))
);
```

**好处**：新平台 = 插一行 `platforms` + 放一个 YAML，**数据库零改动**。

## 六、MCP：设计目的

### `mcp/server.py` —— 让 AI 在系统外部

**设计目的**：**AI 不在应用内部。**

传统做法是把 AI 嵌进应用，AI 和数据库绑死，用户只能用这个 App 预设的问法。

我们的做法：AI 在外面（用用户自己的 Claude / 豆包），通过 MCP 连进来。

**好处**：用户换 AI、换问法、换角度，账本不用动。

---

### 工具数量从 11 个开始 —— 少即是多

AI 面对 50 个工具会懵，面对 11 个会用。第一轮只给必需的。

| 工具 | 写权限 |
|---|---|
| `import_bill` | ✅ INSERT 原始层（唯一允许的原始写入） |
| `set_override` | ✅ UPSERT 修正层 |
| 其余 9 个 | ❌ 全部只读 |

---

### 写权限边界

**11 个工具里只有 2 个能写**，而且：

1. `set_override` 直接调 `overrides.set_override()`，**不自己拼 SQL**
2. 工具 schema 里不存在原始字段名
3. 每次写入带 `updated_by='mcp'`，日志可查

**MCP 想改原始数据？物理上没有路径。**

## 七、契约：`schemas.py` 为什么是唯一真相源

```
        schemas.py
             │
     ┌───────┼────────┬──────────┐
     ↓       ↓        ↓          ↓
  FastAPI  OpenAPI  MCP工具    前端types.ts
  (校验)   (/docs)  (AI读的)    (队友抄的)
```

**同一个东西，四种投影。改一处，四处同步。**

### 具体怎么用

队友拿到后端的操作流程：

```bash
pip install -r requirements.txt
uvicorn backend.main:app --reload
```

打开 `http://localhost:8000/docs`：

- 所有 11 个接口
- 每个字段的类型和说明（来自 `Field(description=...)`）
- **能直接点"Try it out"看到真实返回的 JSON**
- 一份可导入 Postman

**他不需要问任何人。Swagger 是活的，永远不会过期。**
