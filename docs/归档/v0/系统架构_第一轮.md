# 系统架构（第一轮）

> 本文档定义**第一轮**要交付的系统：一套可运行的、跨平台账单导入 + 固定格式报告生成 + MCP 接入的最小闭环。
> 第一轮不做智能判断（不追问、不决策建议），但**数据结构必须为智能层预留入口**。
>
> 配套文档：
> - `01_原始账单格式.md` —— 原始字段来源与归一化
> - `03_功能审计.md` —— 报告组件需要的字段与现有字段的对照
> - `../02_账单页面设计.md` —— 报告页面的 UI 结构

---

## 一、第一轮要解决什么

四件事，一件不多：

| # | 能力 | 验收标准 |
|---|---|---|
| 1 | **跨平台账单导入** | 微信 `.xlsx` + 支付宝 `.csv`/`.zip` 都能导入，同一笔不重复入账 |
| 2 | **生成 preset 报告** | 支出/收入 × 周/月/年 的全部预置组件都能出数 |
| 3 | **MCP 操控以上全部** | AI 能通过 MCP 触发导入、查询报告、改数据 |
| 4 | **MCP 可写特殊字段** | AI 能改手动大类/小类/豁免标记，**但碰不到原始字段** |

第 4 条是这一轮最关键的设计约束：**MCP 有写权限，但写不到原始层。**

## 二、四层结构

```
┌─────────────────────────────────────────────────────────────┐
│  前端（Web）                                                │
│  账单报告页 · 导入页 · 数据修正页                             │
└──────────────────────────┬──────────────────────────────────┘
                           │ HTTP / JSON
┌──────────────────────────▼──────────────────────────────────┐
│  后端（API 层）                                              │
│  导入解析 · 报告查询 · 字段修正 · 权限校验                     │
└──────────────┬────────────────────────────┬─────────────────┘
               │                            │
┌──────────────▼──────────────┐  ┌──────────▼─────────────────┐
│  MCP Server                │  │  数据库（SQLite）           │
│  暴露工具给外部 AI           │  │  原始层（只读）              │
│  调用同一套后端逻辑           │  │  修正层（可写）              │
└─────────────────────────────┘  └────────────────────────────┘
```

**关键约束：前端和 MCP 走同一条后端逻辑，不允许各写一套。**
前端点"改分类"和 AI 通过 MCP 说"把这笔改成零食"，执行的必须是同一个 API。

## 三、数据库分层：原始层与修正层

这是整个设计的地基。**第一轮所有字段决策都服务于这一条：原始数据不可变。**

### 3.1 原始层（immutable，写入后永不 UPDATE）

来源：`01_原始账单格式.md` 的 11 个字段 + remark。

```sql
CREATE TABLE transactions_raw (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    source       TEXT    NOT NULL,   -- 微信支付 / 支付宝
    tx_time      TEXT    NOT NULL,   -- YYYY-MM-DD HH:MM:SS
    direction    TEXT    NOT NULL,   -- 支出 / 收入 / 中性
    amount       REAL    NOT NULL,   -- 恒为正
    pay_method   TEXT,
    counterparty TEXT,
    item         TEXT,
    tx_type      TEXT,               -- 平台原始分类
    status       TEXT,
    tx_no        TEXT,
    merchant_no  TEXT,
    remark       TEXT,
    -- 派生字段（导入时推导，不人工填）
    date         TEXT    NOT NULL,
    month        TEXT    NOT NULL,
    weekday      INTEGER NOT NULL,
    hour         INTEGER NOT NULL,
    -- 导入元信息
    dedupe_key   TEXT    NOT NULL UNIQUE,
    raw_json     TEXT,               -- 原始整行，永久留底
    imported_at  TEXT    NOT NULL,
    CHECK (direction IN ('支出','收入','中性'))
);
```

**这一张表没有 UPDATE 权限。** 后端代码层面禁止对它执行 `UPDATE`/`DELETE`，只允许 `INSERT`。

### 3.2 修正层（mutable，AI 和前端都能写）

```sql
-- 人工/AI 对单笔交易的所有修正，都落在这张表
CREATE TABLE tx_overrides (
    tx_id            INTEGER PRIMARY KEY
                     REFERENCES transactions_raw(id) ON DELETE CASCADE,
    manual_category  TEXT,      -- 手动大类，覆盖映射结果
    manual_subcat    TEXT,      -- 手动小类
    is_exempt        INTEGER DEFAULT 0,  -- 豁免：不算消费/不算收入
    exempt_reason    TEXT,      -- 豁免理由
    funding          TEXT DEFAULT '自有',  -- 自有/亲情卡/他人代付
    note             TEXT,      -- 单笔备注
    updated_by       TEXT,      -- 'ui' / 'mcp' / 'agent:<name>'
    updated_at       TEXT
);

-- 分类映射规则（机械层出报告时用；改了重跑即可，不改数据）
CREATE TABLE category_rules (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    major         TEXT NOT NULL,   -- 大类：餐饮/交通/医疗...
    minor         TEXT,            -- 小类：美团/某快餐...
    match_field   TEXT NOT NULL,   -- tx_type / item / counterparty / pay_method
    match_op      TEXT NOT NULL,   -- equals / contains / regex
    match_value   TEXT NOT NULL,
    priority      INTEGER DEFAULT 100,
    enabled       INTEGER DEFAULT 1,
    version       INTEGER DEFAULT 1,  -- 规则版本
    created_by    TEXT,            -- ui / mcp
    updated_at    TEXT
);

-- 口径配置（"这个月花了多少"按哪套规则算）
CREATE TABLE stats_config (
    rule_key    TEXT PRIMARY KEY,
    rule_value  TEXT,
    description TEXT,
    version     INTEGER DEFAULT 1,
    updated_at  TEXT
);
```

### 3.3 两层如何合并查询

报告查询不直接读 `transactions_raw`，而是读一个**视图**：

```sql
CREATE VIEW v_tx AS
SELECT
    r.*,
    -- 分类：手动 > 规则映射 > 平台原始
    COALESCE(o.manual_category,
             (SELECT cr.major FROM category_rules cr
              WHERE cr.enabled=1 AND cr.priority<100
                AND CASE cr.match_op
                    WHEN 'equals'    THEN r.[field] = cr.match_value
                    WHEN 'contains'  THEN r.[field] LIKE '%'||cr.match_value||'%'
                    WHEN 'regex'     THEN r.[field] REGEXP cr.match_value
                END
              ORDER BY cr.priority LIMIT 1),
             r.tx_type)        AS category,
    COALESCE(o.manual_subcat, '') AS subcat,
    COALESCE(o.is_exempt, 0)      AS is_exempt,
    COALESCE(o.funding, '自有')   AS funding,
    COALESCE(o.note, '')          AS note
FROM transactions_raw r
LEFT JOIN tx_overrides o ON o.tx_id = r.id;
```

**好处**：改了 `category_rules` 或 `tx_overrides`，视图立刻反映新口径，**原始数据一个字节没动**。账单可以重跑，历史不会消失。

## 四、后端 API

### 4.1 导入类

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/import/preview` | 上传文件，返回"检测到 N 笔，来源 X，日期范围 A~B"，不入库 |
| POST | `/api/import/commit` | 确认入库，返回新增/跳过笔数 |
| GET | `/api/import/history` | 导入历史（谁在什么时候导了什么） |

### 4.2 报告类（preset 报告）

全部是**只读 GET**，参数化查询，不接受任意 SQL。

| 路径 | 对应组件 |
|---|---|
| `/api/report/summary` | 周期总览（总额、环比、笔数） |
| `/api/report/calendar` | 每日日历 |
| `/api/report/trend` | 近 N 期柱状图 + 均值线 |
| `/api/report/by-category` | 分类环形图 + 二级列表 |
| `/api/report/by-method` | 支出方式分组 |
| `/api/report/income-rank` | 收入排行 |
| `/api/report/transactions` | 明细列表（支持 date/month/category/subcat/pay_method 筛选） |

**通用参数**：`type`（expense/income）、`period`（week/month/year）、`value`（2026-09 / 2026-W38 / 2026）。

### 4.3 修正类

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/tx/{id}` | 单笔详情（含原始 + 修正两层） |
| PATCH | `/api/tx/{id}/override` | 改 manual_category / manual_subcat / is_exempt / funding / note |
| GET/POST/PATCH/DELETE | `/api/rules` | 分类映射规则 CRUD |
| GET/PATCH | `/api/config` | 口径配置读写 |

**PATCH 的硬约束**：请求体里如果出现 `source` / `tx_time` / `direction` / `amount` / `pay_method` / `counterparty` / `item` / `tx_type` / `status` / `tx_no` / `merchant_no` / `remark` **任何一个，直接 403 拒绝**。

## 五、MCP Server

### 5.1 暴露的工具

| 工具 | 对应后端 | 说明 |
|---|---|---|
| `import_bill` | `/api/import/*` | 导入微信/支付宝账单 |
| `query_summary` | `/api/report/summary` | 周期总额 |
| `query_calendar` | `/api/report/calendar` | 每日明细 |
| `query_trend` | `/api/report/trend` | 趋势 + 均值 |
| `query_by_category` | `/api/report/by-category` | 分类统计 |
| `query_by_method` | `/api/report/by-method` | 支出方式 |
| `query_income_rank` | `/api/report/income-rank` | 收入排行 |
| `query_transactions` | `/api/report/transactions` | 明细查询 |
| `set_override` | `/api/tx/{id}/override` | **改单笔修正字段** |
| `manage_rule` | `/api/rules` | **增删改分类映射规则** |
| `set_config` | `/api/config` | **改口径配置** |

### 5.2 写权限的硬边界

MCP 能调的写工具只有三个，且**全部只作用于修正层**：

```
允许写入：tx_overrides / category_rules / stats_config
禁止写入：transactions_raw（无任何工具暴露 UPDATE 路径）
```

**验证方式**：`set_override` 的 schema 里根本不存在原始字段名；后端再校验一次；日志记录每次写入的 `updated_by`。

## 六、为什么这样分层

### 6.1 原始数据不可变，是为了"可核查"

从真实账本实践里学到的教训：**数字错了你必须能查清楚是哪一步错的。**
如果 AI 能改原始字段，一旦报表对不上，你分不清是解析错了还是 AI 改错了。

### 6.2 修正层独立，是为了"口径可迭代"

真实账本里有大量反复修正的案例：

| 案例 | 修正方式 | 不该做的做法 |
|---|---|---|
| "某高校天猫校园店"其实不是教材是零食 | 改 `manual_category` | 改 `item` 原文 |
| 药房消费被误判成餐饮 | 改 `category_rules` 关键词 | 改原始 `tx_type` |
| 关键词「华颐」误抓售货机 | 收窄规则为「华颐医疗」 | 删原始记录 |
| 口令红包是资金调拨不是消费 | 设 `is_exempt=1` | 删掉这笔 |

**改规则和改标注，历史报表重跑即可。** 原始凭证永远在，任何时候能回溯。

### 6.3 MCP 走同一套后端，是为了"两个入口一条路"

前端能做的 MCP 都能做，反之亦然。否则会出现"前端显示 A，AI 算出 B"，口径立刻分裂。

## 七、第一轮不做的事

| 不做 | 原因 | 何时做 |
|---|---|---|
| AI 主动追问用户 | 需要智能层 | 第二轮 |
| 自动分类 | 需要 LLM | 第二轮（MCP 侧做，前端只显示结果） |
| 决策建议（今天还能花多少） | 需要用户约束建模 | 第三轮 |
| 多账户余额管理 | 单账户已能验证闭环 | 视需要 |
| 规则版本历史回溯 | 第一轮 `version` 字段先占位 | 第二轮 |
| 大额消费/自动扣款等支付宝内部标签 | **原始数据里没有，无法绕过** | 不做 |

## 八、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 数据库 | SQLite | 单文件、零部署、事务够用；`transactions_raw` 十万行级别毫无压力 |
| 后端 | FastAPI（或 Django REST） | 自动生成 OpenAPI，MCP 工具 schema 可直接复用 |
| MCP | Python MCP SDK | 与后端同语言，工具定义可从后端路由自动派生 |
| 前端 | Vue3 + ECharts | ECharts 环形图/柱状图/日历热力图都是现成的 |
| 导入解析 | openpyxl（微信）+ 编码探测（支付宝） | 都是标准库级方案 |

> 队友 PPT 里写的是 Django REST Framework。如果按 PPT 走，用 DRF 也完全可以，MCP Server 用 Python SDK 照样接得上。**选 Django 还是 FastAPI 不影响架构，只影响代码组织。**

## 九、数据流：一次完整的查询

以"MCP 被问『9月花了多少』"为例：

```
AI (Claude / 豆包 / 任何 MCP 客户端)
  ↓ 调用 query_summary(type=expense, period=month, value=2026-09)
MCP Server
  ↓ 调用后端 HTTP API（同一套逻辑，前端也走这条）
后端
  ↓ SELECT SUM(amount), COUNT(*) FROM v_tx
     WHERE direction='支出' AND is_exempt=0 AND month='2026-09'
数据库 (v_tx 视图 = transactions_raw LEFT JOIN tx_overrides + category_rules)
  ↓ 返回 {total: 1900.00, count: 82, prev: 2800.00, delta: -900.00}
MCP Server → AI
  ↓ AI 自己决定怎么措辞
"9月支出 ¥1900.00，共 82 笔，比 8 月少花了 ¥900.00（-32.1%）。"
```

**注意最后一步：措辞是 AI 决定的，数字是后端算的。**
这就是"AI suggest, rules decide"在代码里的落地形态。

## 十、验收清单

第一轮完成的判据，逐条可测：

- [ ] 导入一份微信 `.xlsx`，`transactions_raw` 写入 N 行，`raw_json` 完整保留

- [ ] 原始表的 11 个字段，`raw_json` 与源文件逐字节对应
- [ ] MCP 调用 `query_summary` 的返回值，与前端页面上显示的数字一致

- [ ] 前端改分类和 MCP 改分类，在 `tx_overrides.updated_by` 里分别看到 `ui` / `mcp`
