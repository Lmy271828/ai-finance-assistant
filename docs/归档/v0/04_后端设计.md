## 三、`db.py` —— 连接管理、建表、视图、事务

### 3.1 它必须做的五件事

| 职责 | 不做的后果 |
|---|---|
| 执行 `schema.sql` 建表建视图 | 新人/CI 拿到空库，报错出现在业务跑到一半时 |
| 绝对路径解析 | 相对路径写错地方，SQLite 默默建新空库，症状是"数据不见了" |
| `row_factory = sqlite3.Row` | 到处 `row[3]` 魔法下标，改列序全线崩溃 |
| WAL + busy_timeout | FastAPI 多线程下偶发 `database is locked`，极难复现 |
| 事务上下文管理器 | **导入中断导致静默丢数据** |

### 3.2 接口

```python
DB_PATH: Path                    # 模块级常量，导入一次
SCHEMA_PATH: Path                # db/schema.sql 位置

def init_db() -> None:
    """建表 + 建索引 + 建视图。幂等，可重复执行。"""

def get_conn() -> sqlite3.Connection:
    """返回配置好的连接：Path(str(DB_PATH)), row_factory=Row, PRAGMA 已设"""

@contextmanager
def transaction():
    """BEGIN ... COMMIT / ROLLBACK。异常时回滚。"""
```

### 3.3 事务为什么不可省

导入 1200 笔，第 830 笔解析失败。

- **无事务**：库里留下 1~846 笔残缺数据，界面显示"9月 846 笔"，看起来正常，但少了 354 笔且**永久丢失**（下次重导会被 `dedupe_key` 跳过）
- **有事务**：整体 ROLLBACK，返回明确错误"第 847 行解析失败，已回滚，未写入任何数据"

**要么全进，要么全不进。** 这是本项目最不能妥协的一条。

### 3.4 原始层的不可变性从哪来

不靠"大家记得别 UPDATE"，靠三道：

1. **表结构里没有触发器去拦**（因为业务确实需要能读到它）
2. **代码里没有任何 `UPDATE transactions_raw` / `DELETE FROM transactions_raw`**
3. **`tests/test_immutability.py` 断言这条**（详见第八节）

## 四、`schemas.py` —— 输入输出的合法形状

### 4.1 为什么这个文件最不能省

它同时解决三个问题：

1. **MCP 工具 schema 的来源** —— AI 连接时读 schema 才知道有哪些工具、参数叫什么名。不定义 = AI 瞎
2. **前端有类型** —— 不定义 = 返回 dict 的 key 拼错也不报错
3. **脏参数入口拦截** —— 不定义 = 拼错的参数打到最后才崩，甚至返回空结果让 AI 给出错误答案

### 4.2 通用请求基类

```python
from typing import Literal
from pydantic import BaseModel, Field

Period = Literal['week', 'month', 'year']
Type_ = Literal['expense', 'income']

class ReportReq(BaseModel):
    """所有报告接口的公共入参"""
    type:   Type_
    period: Period
    # week: 2026-W38 | month: 2026-09 | year: 2026
    value:  str = Field(pattern=r'^\d{4}(-\d{2})?(-\d{2})?$')
```

### 4.4 写入类

```python
class OverrideIn(BaseModel):
    """注意：这里没有一个原始字段名。"""
    manual_category: str | None = None
    manual_subcat:   str | None = None
    is_exempt:       bool     = False
    funding:         str      = '自有'

class OverrideResp(BaseModel):
```

**这是刻意的：`OverrideIn` 里根本没有 `amount` / `tx_time` / `direction` 这些字段名。** 即使有人绕过 MCP 直接调 HTTP，Pydantic 默认会**丢弃**未声明的字段（不会报错，但也不会生效）。403 校验是第二道保险。

## 五、`overrides.py` —— 写修正的唯一入口

### 5.1 为什么这个文件存在

前端和 MCP **都能改修正数据**。如果各自写一份写入逻辑，那句"原始字段一个都不许碰"的校验就得写两遍。

```
main.py 的路由处理函数    → 自己写一遍校验  ✅
mcp/server.py 的工具函数  → 自己写一遍校验  ❌ 忘了
```

结果是 **AI 那条路没拦住**，AI 通过 MCP 把一笔 32 块的支出改成 3.2 块，账本从此不可信——而这正是我们对外宣称的核心卖点。

**卖点不能靠自觉守，必须靠结构守。**

### 5.2 设计

```python
# 绝对不允许出现在 OverrideIn 里的字段名
FORBIDDEN_FIELDS = frozenset({
    'id', 'source', 'tx_time', 'direction', 'amount',
    'pay_method', 'counterparty', 'item', 'tx_type',
    'status', 'tx_no', 'merchant_no', 'remark',
    'date', 'month', 'weekday', 'hour',
    'dedupe_key', 'raw_json', 'imported_at',
})


def set_override(tx_id: int, data: OverrideIn,
                 updated_by: str) -> OverrideResp:
    """
    唯一写入口。updated_by: 'ui' / 'mcp' / 'test'
    """
    payload = data.model_dump(exclude_none=True)

    # 防御 1：显式黑名单（防 Pydantic 配置被改宽）
    bad = payload.keys() & FORBIDDEN_FIELDS
    if bad:
        raise ForbiddenFieldError(sorted(bad))

    # 防御 2：tx_id 必须存在于原始层
    if not exists_raw(tx_id):
        raise TxNotFound(tx_id)

    # 防御 3：UPSERT，只碰 tx_overrides
    with db.transaction() as conn:
        conn.execute(
            "INSERT INTO tx_overrides "
            "(tx_id, manual_category, manual_subcat, is_exempt,"
            " funding, note, updated_by, updated_at) "
            "VALUES (?,?,?,?,?,?,?,datetime('now')) "
            "ON CONFLICT(tx_id) DO UPDATE SET "
            " manual_category=excluded.manual_category,"
            " manual_subcat=excluded.manual_subcat,"
            " is_exempt=excluded.is_exempt,"
            " funding=excluded.funding,"
            " note=excluded.note,"
            " updated_by=excluded.updated_by,"
            " updated_at=datetime('now')",
            (tx_id, payload.get('manual_category'),
             payload.get('manual_subcat'), int(payload.get('is_exempt', 0)),
             payload.get('funding', '自有'), payload.get('note'), updated_by),
        )

    return get_override(tx_id)
```

### 5.3 三道防线

| 防线 | 位置 | 作用 |
|---|---|---|
| ① Schema 不含原始字段 | `schemas.py` | MCP 和前端拿不到这些字段名 |
| ② 运行时黑名单 | `overrides.py` | 万一 Pydantic 配宽了，这里再挡一次 |
| ③ 结构上够不到 | SQL 语句 | `overrides.py` 里**不存在**任何针对 `transactions_raw` 的 UPDATE/DELETE 代码路径 |

**第 ③ 条最硬。** 前两条是约定，第三条是物理事实——就算前两条被绕过，代码里也没有那条路径。

### 5.4 读接口

```python
def get_override(tx_id: int) -> OverrideResp
def list_overrides(filter: dict) -> list[OverrideResp]
```

以及给报告用的视图（定义在 `schema.sql`）：

```sql
CREATE VIEW v_tx AS
SELECT
    r.id, r.source, r.date, r.month, r.weekday, r.hour,
    r.direction, r.amount, r.pay_method, r.counterparty,
    r.item, r.tx_type, r.status, r.remark,
    COALESCE(o.manual_category, r.tx_type)  AS category,
    COALESCE(o.manual_subcat, '')           AS subcat,
    COALESCE(o.is_exempt, 0)                AS is_exempt,
    COALESCE(o.funding, '自有')             AS funding,
    COALESCE(o.note, '')                    AS note
FROM transactions_raw r
LEFT JOIN tx_overrides o ON o.tx_id = r.id;
```

**第一轮这个视图是纯 LEFT JOIN，没有规则匹配子查询**——因为 `category_rules` 表不存在。分类直接 `COALESCE(manual_category, tx_type)`。

### 6.1 原则

> **`main.py` 里不出现任何业务逻辑。**
> 如果看到 `if month == '2026-09':`，说明逻辑漏进来了，挪到 `reports/` 去。

### 7.2 写权限边界

**11 个工具里只有 2 个能写**：`import_bill`（插原始层）和 `set_override`（写修正层）。

而且：

- 没有任何工具的 schema 里出现原始字段名
- `set_override` 直接调 `overrides.set_override()`，**不自己拼 SQL**
- 每个写入都带 `updated_by='mcp'`，日志可查

**MCP 想改原始数据？物理上它没有任何一条路径可以走通。**

### 7.3 两个入口一条路

```
前端点"改分类"  → PATCH /api/tx/1/override → overrides.set_override(..., 'ui')
AI 说"这笔改零食" → tool: set_override        → overrides.set_override(..., 'mcp')
        ↓
   同一份代码、同一个校验、同一张表，只是 updated_by 不同
```

不存在"前端显示 A，AI 算出 B"的可能。

## 十、明确推迟到第二轮的东西

| 东西 | 为什么现在不做 |
|---|---|
| `category_rules` 表 + `rules.py` | 分类映射是智能判断，第一轮用 `tx_type` 顶 |
| `stats_config` 表 + `config.py` | 口径版本化需要先有"用户会改口径"这个真实需求 |
| AI 主动追问 | 需要智能层 |
| 决策建议（今天还能花多少） | 需要用户约束建模 |

**这四张表/四个模块都留了位置（架构文档里有），但代码里一行都不写。**
先让闭环跑起来——导入能跑、报告能出、AI 能改——再加智能。
