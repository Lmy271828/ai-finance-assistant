# 功能审计：字段够不够

> 文档目的：对着每个页面组件，逐个检查"需要什么数据"和"现有字段能不能提供"。
> 现有字段：11 个原始只读字段（source / tx_time / direction / amount / pay_method / counterparty / item / tx_type / status / tx_no / merchant_no）+ remark + 3 个派生字段（date / month / weekday）。

---

## 现有字段清单

**原始只读（导入时写入，不修改）**

| # | 字段 | 说明 |
|---|---|---|
| 1 | `source` | "微信支付" / "支付宝" |
| 2 | `tx_time` | "YYYY-MM-DD HH:MM:SS" |
| 3 | `direction` | "支出" / "收入" / "中性" |
| 4 | `amount` | 恒为正 |
| 5 | `pay_method` | 原始支付方式字符串 |
| 6 | `counterparty` | 交易对方 |
| 7 | `item` | 商品说明 |
| 8 | `tx_type` | 平台原始分类 |
| 9 | `status` | "交易成功" / "已退款" 等 |
| 10 | `tx_no` | 交易单号（去重 key） |
| 11 | `merchant_no` | 商户单号（去重兜底 key） |
| — | `remark` | 用户备注（透传） |

**派生字段（导入时从 tx_time 自动推导，不需人工填）**

| 字段 | 推导方式 |
|---|---|
| `date` | `tx_time[0:10]` → "YYYY-MM-DD" |
| `month` | `tx_time[0:7]` → "YYYY-MM" |
| `weekday` | `tx_time` 推导，0=周日 |

---

## 审计结果

---

### 组件 1：每日日历（支出/收入）

**需要的数据**：每个日期 + 该日支出/收入的 sum(amount)

**字段够不够**：

| 检查项 | 结论 |
|---|---|
| 日期范围 | ✅ `date` 直接提供 |
| 每日 sum(amount) | ✅ `date` + `amount` + `direction` 过滤即可 |
| 今天是哪天 | ✅ 前端用 `new Date()` 判断，不需要数据库字段 |
| 今天高亮 | ✅ 前端判断 |
| 周期内无消费日期 | ✅ 直接算，sum=0 的日期留空或显示"－" |

**结论：✅ 足够，无需额外字段。**

---

### 组件 2：周期总览（总支出/收入 + 较上周期变化）

**需要的数据**：
- 当前周期 sum(amount)
- 上个周期 sum(amount)
- 当前周期 count(*)
- 变化值 = 当前 - 上个，变化率 = (当前 - 上个) / 上个 × 100%

**字段够不够**：

| 检查项 | 结论 |
|---|---|
| 当前周期 sum | ✅ `direction` + `date`/`month`/`year` 过滤后 `SUM(amount)` |
| 上个周期 sum | ✅ 同上，时间偏移一个周期即可 |
| 笔数 | ✅ `COUNT(*)` |
| 对比绝对值和百分比 | ✅ 前端算，不需要数据库额外字段 |

**结论：✅ 足够，无需额外字段。**

---

### 组件 3：月度柱状图（近5月支出/收入对比）

**需要的数据**：近5个月每个月的 sum(amount)

**字段够不够**：

| 检查项 | 结论 |
|---|---|
| 月份范围 | ✅ `month` 字段支持范围查询 |
| 每月 sum | ✅ `month` + `amount` 聚合 |
| 月均参考线 | ✅ 所有月份 `AVG(sum_per_month)`，前端算或 SQL 窗口函数 |

**结论：✅ 足够，无需额外字段。**

---

### 组件 4：分类环形图 + 分类列表

**需要的数据**：每个分类的 sum(amount) + 占比

**问题**：我们只有 `tx_type`（平台原始分类），它很粗，不能直接对应我们要展示的细分类（如"餐饮美食"、"教育培训"）。

| 检查项 | 结论 |
|---|---|
| 平台原始粗分类 | ✅ `tx_type` 直接可用 |
| 我们展示的细分类 | ❌ **没有这个字段**——需要从 `tx_type` + `item` + `counterparty` 映射得到 |
| 每类 sum + 占比 | ✅ 映射后直接聚合 |

**映射规则举例**：

| 我们分类 | 命中关键词（`item` / `counterparty` / `tx_type`） |
|---|---|
| 餐饮美食 | item 含"美团"、"饿了么"、"麦当劳"、"餐厅"，tx_type="餐饮" |
| 交通出行 | item 含"地铁"、"公交"、"打车"，tx_type="交通" |
| 购物 | tx_type="购物" |
| 医疗健康 | item 含"医院"、"药店" |
| ... | ... |

**结论：⚠️ 字段本身够，但需要分类映射规则（写在配置文件里，不是数据库字段）。**

---

### 组件 5：支出方式分组

**需要的数据**：每个 `pay_method` 的 sum(amount) + count(*)

**字段够不够**：

| 检查项 | 结论 |
|---|---|
| 按支付方式分组 | ✅ `pay_method` 直接提供 |
| 每组 sum + count | ✅ `pay_method` + `amount` 聚合 |
| 亲情卡单独展示 | ✅ `pay_method` 含"亲情卡"可单独过滤 |

**结论：✅ 足够，无需额外字段。**

---

### 组件 6：收入排行

**需要的数据**：所有 `direction`='收入' 的交易，按 amount 降序

| 检查项 | 结论 |
|---|---|
| 过滤收入 | ✅ `direction`='收入' |
| 按金额排序 | ✅ `ORDER BY amount DESC` |
| 排名 | ✅ 前端 enumerate，无需数据库字段 |
| 每行显示：金额、时间、来源、分类 | ✅ `amount` + `date` + `counterparty` + `tx_type` |

**结论：✅ 足够，无需额外字段。**

---

## 总结

| 组件 | 状态 | 需要的额外东西 |
|---|---|---|
| 每日日历 | ✅ 够 | 无 |
| 周期总览 | ✅ 够 | 无 |
| 月度柱状图 | ✅ 够 | 无 |
| 分类环形图+列表 | ⚠️ 够，但需映射规则 | 分类映射配置（不在数据库） |
| 支出方式分组 | ✅ 够 | 无 |
| 收入排行 | ✅ 够 | 无 |

**结论：11 个原始字段 + 3 个派生字段，足以支撑全部 6 个组件。唯一需要的是分类映射规则（Python dict 配置，不是数据库字段）。**

---

## 缺失的字段（但可以绕过）

| 想做的功能 | 缺失什么 | 绕过去 |
|---|---|---|
| 大额消费单独统计 | 支付宝内部标注字段 | **无法绕过**——原始数据里没有"大额"标记，需要人工标注或 AI 判断 |
| 自动扣款识别 | 支付宝内部标注字段 | 同上 |
| 先买后付识别 | 支付宝内部标注字段 | 同上 |
| 分期付款识别 | 支付宝内部标注字段 | 同上 |
| 省钱建议 | 优惠抵扣记录 | **无法绕过**——原始账单不含优惠前原价，需要对账或单独录入 |

这些都是支付宝自己掌握的业务标签，我们导出的原始数据里**没有这些字段**。如果要做这几项，只能：① 人工逐笔标注 ② 接入支付宝内部 API（如果有）。**机械层目前不做这几项。**
