## 1. 基础约定

| 项 | 约定 |
|---|---|
| BaseURL | `/api`（开发走 vite proxy，前端代码里不要出现 `localhost:8000`） |
| 编码 | UTF-8 JSON |
| 认证 | 第一轮无 |
| 时间格式 | 全部 `YYYY-MM-DD` 或 `YYYY-MM-DD HH:MM:SS`，**不用时区**，按本地时间存 |
| 区间标识 | week `2026-W38` / month `2026-09` / year `2026` |

---

## 2. 数值约定 ⚠️ 最容易搞错的地方

### 2.1 金额

| 项 | 约定 |
|---|---|
| 单位 | **元**（不是分） |
| 类型 | `float` |
| 精度 | 两位小数 |
| 谁四舍五入 | **服务端** `round(x, 2)`，前端不要二次处理 |

> 前端再做一次 `toFixed(2)`，两边算法不一致时会差 1 分。

### 2.2 百分比

| 项 | 约定 |
|---|---|
| `rate` / `pct` / 占比 | **百分数**：`17.2` 表示 17.2%，`100.0` 表示 100% |
| 不是 | 小数（`0.172` 是错的） |

> 如果你看到 `pct: 25.0` 就知道是 25%，不用再乘 100。

### 2.3 分母

`pct` 的分母永远是 `CategoryResp.total`，也就是**该周期该收支方向的全量合计**。

不是"各大类之和"（虽然它们相等），而是**含未分类项的全量**。所以各大类 pct 加起来可能 **小于 100**，差额是"未匹配到分类"的部分。

## 3. 空值与空集合约定 ⚠️ 第二个坑

这三条必须一致，否则前端会拿到 `undefined` 崩掉：

| 情况 | 返回 | 不要返回 |
|---|---|---|
| 某字段没有值 | `""`（空字符串）或 `null` | ~~字符串 `"null"`~~ |
| 某个列表为空 | `[]` | ~~`null`~~ |
| **日历中某天无消费** | **该日期整个不出现** | ~~`{"amount": 0}`~~ |

### 为什么日历要特殊

一个月的日历有 28-31 格。如果每天都返回，`count=0` 的格子和"没数据"混在一起，前端无法区分"这天确实 0 支出"和"这天数据没导全"。

**不返回 = 让前端自己补零，同时天然暴露"这几天库里没数据"。**

## 4. 排序规则

| 接口 | 排序 |
|---|---|
| `calendar` | `days` 按 `date` **升序** |
| `trend` | `bars` 按 `label` **升序** |
| `by-category` | `majors` 按 `amount` **降序**；`minors` 按 `amount` **降序** |
| `by-method` | `groups` 按 `amount` **降序** |
| `income-rank` | `items` 按 `amount` **降序** |
| `transactions` | `items` 按 `tx_time` **降序**（新的在前） |

## 5. 各接口的边界行为

### `GET /api/report/summary`

- 上期基准：week→上一周 / month→上一月 / year→上一年
- `prev = 0` 时 → `rate` 返回 `null`（**不是 0**），前端显示 `—`
- 当期无数据 → `total=0, count=0`，**不是 404**

### `GET /api/report/calendar`

- 返回该周期内所有 `is_exempt=0` 的日期
- 按 `date` 分组求和，跨支付方式累加
- 详见第 3 节的空日期约定

### `GET /api/report/trend`

- `n` 默认 5，指**包含当期在内的最近 n 个周期**
- 当期未过完也照常返回（9 月 30 号看 9 月，拿到的是截至今天的部分数据）
- `avg` = `bars` 里所有 `amount` 的算术平均，**不是** `total / n`
  - 某个 bar 为 0 也参与平均（它是真实存在的一个区间）

### `GET /api/report/by-category`

- `category` 来源优先级：`manual_category` > `tx_type` > `'其他'`
- 第一轮**没有分类映射规则表**，所以 `major` 基本等于平台原始分类
- `minors` 只有当 `tx_overrides.manual_subcat` 被人工填过才有值
- **`tx_ids` 上限 200 个**，超出时返回前 200，前端点击应改用 `transactions` 接口过滤

### `GET /api/report/by-method`

- 按 `pay_method` **原始字符串**分组，不做归并
  - `储蓄卡(1234)` 和 `储蓄卡(5678)` 是**两组**
  - 前端如果要做视觉归并，自己在客户端合并
- 空 `pay_method` 归到 `""`，不丢

### `GET /api/report/income-rank`

- 只查 `direction='收入'`，最多返回 50 条
- `counterparty` 可能是空字符串（微信的"二维码收款"拿不到对方名）

### `GET /api/report/transactions`

- `include_exempt=false`（默认）→ 被豁免的条目**不出现**
- `keyword` 同时搜 `counterparty` / `item` / `remark`，任一命中即返回
- `date_from`/`date_to` **覆盖** `period`，不是叠加
- 分页最大 `size=200`

## 6. 错误码

| 状态码 | 何时 | 响应 |
|---|---|---|
| 400 | 参数不合法（枚举值错、日期格式错） | `{"detail": [...pydantic 校验信息...]}` |
| 403 | **试图修改原始字段** | `{"detail": "原始字段不可修改: amount"}` |
| 404 | `tx_id` 不存在 | `{"detail": "交易不存在: 99999"}` |
| 500 | 导入事务回滚 | `{"detail": "导入失败，第 847 行金额列无法解析，已回滚，未写入任何数据"}` |

**403 是本项目的招牌行为**，不是异常，是特性。

## 7. 写入接口

### `PATCH /api/tx/{id}/override`

**请求体只能包含这 6 个字段：**

```json
{
  "manual_category": "零食超市",
  "manual_subcat": "校园超市",
  "is_exempt": false,
  "exempt_reason": null,
  "funding": "自有",
  "note": "天猫校园店，不是教材"
}
```

**任何其他字段（包括 `amount`、`tx_time`、`direction`）→ 403。**

行为说明：

| 项 | 约定 |
|---|---|
| 部分更新 | 只传要改的字段，没传的**保持原值**（UPSERT，不是全量覆盖） |
| `updated_by` | 服务端填 `'ui'`，不来自请求体 |
| 该笔从未修过 | 自动 INSERT 一行 |
| 取消修正 | 传 `manual_category: null` 会置空（不是删整行） |
| 彻底删除修正记录 | 第一轮不提供接口 |

### `POST /api/import/commit`

**全事务**：任何一行解析失败 → 整体回滚 → 库表保持导入前状态。

所以 `first_error` 有值时，`inserted` 一定是 0。

## 8. 联调清单

写完前端后，对照这 8 条自查：

- [ ] 金额显示两位小数，没有出现 `1900.0000000001`
- [ ] `rate=17.2` 显示成 `17.2%`，不是 `0.17%`
- [ ] `rate=null` 显示成 `—`，不是 `0%` 或 `NaN%`
- [ ] 日历缺日期的位置有格子（不是整个塌了）
- [ ] 空分类显示 `[]` 时，`.map()` 不报错
- [ ] `counterparty=""` 时不显示空白占位
- [ ] 点击分类跳明细，走的是 `transactions` 接口而不是直接用 `tx_ids`
- [ ] 改一笔分类后，报告数字变化，且**刷新页面后仍然变**（说明写进库了，不是前端本地状态）
